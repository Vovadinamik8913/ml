## 1. Почему обучаем отдельно на каждом из 41 таргета?

### 📖 Простыми словами

**Потому что каждый продукт — это отдельный вопрос «Купит ли клиент?»**

Представь, что ты менеджер банка и тебе нужно предсказать, какие продукты предложить 250 000 клиентам.

У тебя 41 вопрос:
- Купит ли клиент **кредитную карту**?
- Купит ли клиент **депозит**?
- Купит ли клиент **инвестиции**?
- ... (ещё 38 продуктов)

**Ключевой момент:** Эти вопросы **независимы**. Один и тот же клиент может:
- Взять кредитную карту ✅
- Не взять депозит ❌
- Взять инвестиции ✅

**Почему не одна модель на всё?**

Если бы мы сделали одну модель с 41 выходом, она бы училась усреднённо. Но:
- Для **кредитной карты** важны: кредитная история, доходы, траты
- Для **депозита** важны: накопления, возраст, стабильность
- Для **инвестиций** важны: риск-профиль, капитал, грамотность

**Аналогия:** Врач не использует один набор анализов для всех болезней.
- Для сердца → ЭКГ + холестерин
- Для желудка → гастроскопия + кислотность
- Для лёгких → рентген + спирометрия

Каждый диагноз — свой набор тестов. Каждый таргет — своя модель.

---

### 🔬 С точки зрения ML/математики

**Формально:**

У нас **multi-label классификация** (не multi-class!):

```
Multi-class (один класс из N):
  y ∈ {0, 1, 2, ..., N-1}
  Σᵢ P(y=i) = 1  # вероятности суммируются в 1

Multi-label (независимые бинарные таргеты):
  y ∈ {0, 1}^41  # 41 независимый бинарный таргет
  P(y₁=1), P(y₂=1), ..., P(y₄₁=1) — независимые вероятности
```

**Почему 41 отдельная модель:**

#### 1. Независимость таргетов

```
P(y^(i)=1 | y^(j)=1) ≠ P(y^(i)=1)  # таргеты коррелируют, но не детерминируют

Для multi-label:
P(y¹, y², ..., y⁴¹ | X) = Πᵢ P(yⁱ | X)  # предполагаем независимость при условии X
```

#### 2. Разные распределения признаков

```
P(X | y^(1)=1) ≠ P(X | y^(2)=1) ≠ ... ≠ P(X | y^(41)=1)

Пример:
- Для y^(1)=1 (кредитка): X имеет высокий доход, молод возраст
- Для y^(2)=1 (депозит): X имеет высокий баланс, старший возраст

Одна модель пыталась бы выучить усреднённое P(X | y=1), что теряет специфику.
```

#### 3. Разный дисбаланс классов

```
Таргет 1: 10% positive (30k из 750k)
Таргет 2: 0.1% positive (83 из 750k)

Для каждого таргета нужен свой scale_pos_weight, своя балансировка.
```

#### 4. Разные feature importance

```
Для таргета 1: top features = [income, credit_score, age]
Для таргета 2: top features = [balance, deposit_history, pension]

Target-wise feature selection даёт +0.015 AUC (см. BEST_SOLUTION_DETAILED.md)
```

#### 5. Вычислительный компромисс

| Подход | Плюсы | Минусы |
|--------|-------|--------|
| **41 модель с 1 выходом** | Проще архитектура, легче параллелить, легче debug | 41 модель вместо 1 |
| **1 модель с 41 выходом** | Одна модель | Сложнее архитектура, сложнее tuning, хуже AUC |

**Почему не использовали альтернативы:**

| Подход | Почему не подошёл |
|--------|------------------|
| **Multi-output модель** | Сложнее, требует больше данных, не даёт выигрыша в качестве |
| **Chain classifier** | Предполагает causal связь, которой может не быть |
| **One модель на всё** | Теряет специфику таргетов, хуже AUC на 0.02–0.03 |

## 2. Почему в этой задаче LightGBM оказался лучше CatBoost?

### 📖 Простыми словами

**Короткий ответ:** Не обязательно лучше, но для **нашего конкретного решения** подошёл лучше.

**Развёрнуто:**

Представь, что у тебя есть два инструмента:
- **LightGBM** — как спортивная машина: быстрая, лёгкая, требует тонкой настройки
- **CatBoost** — как внедорожник: надёжный, стабильный, работает «из коробки»

В нашей задаче было **три ключевых фактора** в пользу LightGBM:

#### 1. Скорость на этапе отбора признаков

- Нам нужно было обучить **41 таргет × 4 модели = 164 модели**
- LightGBM на CPU: ~15 минут на модель → 41 час всего
- CatBoost на CPU: ~45 минут на модель → 122 часа всего (5 дней!)
- С GPU: LightGBM ~3 мин, CatBoost ~2 мин → разница меньше, но GPU было не всегда доступно

#### 2. Ансамблирование

- Мы обучали 4 модели с **разными гиперпараметрами** для каждого таргета
- LightGBM легче настраивать массово (проще параметры, быстрее итерация)
- CatBoost требует больше памяти на модель (при 2440 признаках — критично)

#### 3. Память

- 2440 признаков × 750k строк = огромная матрица
- LightGBM использует меньше RAM (гистограммы + leaf-wise)
- CatBoost требует больше памяти (особенно с категориалками, даже если их нет)

**Но важно:** CatBoost показал бы **сопоставимое качество** (AUC ~0.823–0.825 против 0.827). Разница не в качестве, а в **практичности** для нашего пайплайна.

**Аналогия:** Ты выбираешь между:
- Ferrari (LightGBM): быстрее, но нужно уметь водить
- Toyota (CatBoost): надёжнее, прощает ошибки

Для гонки на 164 круга (164 модели) ты выберешь Ferrari, если умеешь водить.

---

### 🔬 С точки зрения ML/математики

**Формально:**

Сравним для нашей задачи (750k × 2440, 41 таргет):

| Критерий | LightGBM | CatBoost |
|----------|----------|----------|
| **Сложность обучения** | O(n × d × log(n) × T) | O(n × d × T) |
| **Память** | O(n × d / bins) | O(n × d × cat_features) |
| **Качество (AUC)** | 0.82712 | ~0.823–0.825 (оценка) |
| **Время (GPU)** | 3 мин/модель | 2 мин/модель |
| **Время (CPU)** | 15 мин/модель | 45 мин/модель |

#### Почему LightGBM выиграл в нашем случае:

#### 1. Отсутствие категориальных признаков

```
В наших данных: все признаки уже числовые (float/int)

CatBoost: преимущество в native categorical handling
LightGBM: не проигрывает, т.к. encoding уже сделан

Итог: главное преимущество CatBoost не использовано.
```

#### 2. Высокая размерность (2440 признаков)

```
LightGBM: colsample_bytree=0.75 → 1830 признаков на дерево
CatBoost: использует все признаки (или random_subspace)

При высокой размерности:
- LightGBM быстрее сходится (leaf-wise)
- CatBoost требует больше итераций (depth-wise)
```

#### 3. Ансамбль из 4 моделей

```
Нам нужно было 4 РАЗНЫЕ модели (разные гиперпараметры).

LightGBM:
- Легко варьировать: num_leaves, learning_rate, n_estimators
- Быстрая итерация → больше экспериментов

CatBoost:
- Меньше параметров для вариации
- Дольше итерация → меньше экспериментов
```

#### 4. Target-wise feature selection

```
Для каждого таргета отбираем 400 лучших признаков.

LightGBM:
- Быстрое вычисление feature importance (gain-based)
- 150 деревьев достаточно для оценки важности

CatBoost:
- Feature Importance требует больше итераций
- Prediction Values Change (PVC) — точнее, но медленнее
```

#### 5. Масштабируемость

```
41 таргет × 4 модели = 164 обучения

LightGBM (CPU):
- 164 × 15 мин = 2460 мин = 41 час
- Параллельно на 8 ядрах: ~5 часов

CatBoost (CPU):
- 164 × 45 мин = 7380 мин = 123 часа
- Параллельно на 8 ядрах: ~15 часов

Разница: 10 часов — это много для итеративной разработки.
```

---

### Когда CatBoost был бы лучше?

| Сценарий | Почему CatBoost |
|----------|----------------|
| Много категориальных признаков (50+) | Native encoding > manual |
| Маленькие данные (<100k строк) | Разница в скорости не критична |
| Нужно out-of-box качество | Меньше tuning требуется |
| Есть GPU и мало памяти | CatBoost на GPU эффективнее |

**Вывод:** LightGBM не «лучше» CatBoost в абсолютном смысле. Он был **практичнее для нашего пайплайна**:
- Быстрее итерация → больше экспериментов
- Меньше памяти → работа на 64 GB RAM
- Легче ансамблирование → 4 модели на таргет

Если бы у нас было:
- 50+ категориальных признаков
- Неограниченное время
- GPU всегда доступно

— CatBoost мог бы выиграть.

## 3. Что означают параметры BASE_PARAMS?

```python
BASE_PARAMS = {
    'objective': 'binary',
    'metric': 'auc',
    'boosting_type': 'gbdt',
    'n_jobs': -1,
    'verbose': -1,
    'device': 'gpu',
    'gpu_platform_id': 0,
    'gpu_device_id': 0,
}
```

### 📖 Простыми словами

Это **базовые настройки**, которые одинаковы для всех 164 моделей (41 таргет × 4 модели).

| Параметр | Простыми словами | Аналогия |
|----------|------------------|----------|
| **`objective: 'binary'`** | Решаем задачу: «да/нет» (купит/не купит) | Как тест с двумя вариантами ответа |
| **`metric: 'auc'`** | Метрика качества — ROC-AUC | Как «процент правильных ответов» |
| **`boosting_type: 'gbdt'`** | Классический градиентный бустинг | Как строить деревья одно за другим |
| **`n_jobs: -1`** | Использовать все ядра CPU | Как нанять всех доступных рабочих |
| **`verbose: -1`** | Не показывать логи обучения | Как «режим тишины» |
| **`device: 'gpu'`** | Обучаться на видеокарте (GPU) | Как использовать мощный двигатель вместо обычного |
| **`gpu_platform_id: 0`** | ID платформы GPU (для систем с несколькими GPU) | Как «какой видеокартой пользоваться» (первой) |
| **`gpu_device_id: 0`** | ID конкретной видеокарты | Как «какой слот видеокарты» (первый) |

---

### 🔬 С точки зрения ML/математики

#### 1. `objective: 'binary'`

**Технически:**

```
Функция потерь (loss function) для бинарной классификации:

L(y, p) = -[y × log(p) + (1-y) × log(1-p)]  # Binary Cross-Entropy

где:
  y ∈ {0, 1} — истинный таргет
  p ∈ (0, 1) — предсказанная вероятность

Градиент для бустинга:
  ∂L/∂p = (p - y) / (p × (1-p))
```

**Почему 'binary', а не 'multiclass':**

```
У нас **multi-label** (41 независимый бинарный таргет).
Каждая модель предсказывает P(yⁱ=1 | X) для одного таргета i.
Не multi-class (где Σ P(y=i) = 1), а 41 отдельная binary задача.
```

**Альтернативы:**

| Objective | Для чего |
|-----------|----------|
| `'binary'` | Бинарная классификация (0/1) |
| `'regression'` | Непрерывная целевая переменная |
| `'multiclass'` | Один таргет с N классами |
| `'rank'` | Learning-to-rank задачи |

---

#### 2. `metric: 'auc'`

**Технически:**

```
ROC-AUC (Area Under ROC Curve):

TPR(threshold) = TP / (TP + FN)  # True Positive Rate
FPR(threshold) = FP / (FP + TN)  # False Positive Rate

AUC = ∫₀¹ TPR(FPR⁻¹(x)) dx  # площадь под кривой TPR от FPR

Интерпретация:
  AUC = 0.5 — случайное угадывание
  AUC = 1.0 — идеальный классификатор
  AUC = 0.827 — в 82.7% случаев правильно ранжирует positive > negative
```

**Почему AUC, а не accuracy:**

```
Дисбаланс классов:
  Таргет 1: 10% positive (75k из 750k)
  Таргет 2: 0.1% positive (83 из 750k)

Accuracy при always predict 0:
  Таргет 1: 90% accuracy (но useless)
  Таргет 2: 99.9% accuracy (но useless)

AUC:
  Таргет 1: 0.5 при random, 0.8+ при хорошем качестве
  Таргет 2: 0.5 при random, 0.7+ при хорошем качестве
  
→ AUC не зависит от дисбаланса, измеряет ранжирующую способность.
```

**Почему не logloss:**

```
Logloss чувствителен к калибровке вероятностей:
  Logloss = -1/n × Σ [y × log(p) + (1-y) × log(1-p)]

Но в соревновании метрика — Macro AUC, оптимизируем её напрямую.
```

---

#### 3. `boosting_type: 'gbdt'`

**Технически:**

```
Gradient Boosting Decision Trees (GBDT):

F₀(x) = 0  # начальное предсказание

Для t = 1 до T:
  1. Вычислить градиенты: gᵢ = ∂L(yᵢ, F(xᵢ)) / ∂F(xᵢ)
  2. Обучить дерево hₜ(x) на градиентах g
  3. Обновить: Fₜ(x) = Fₜ₋₁(x) + η × hₜ(x)

Итог: F(x) = Σₜ η × hₜ(x)
```

**Альтернативы в LightGBM:**

| Boosting Type | Описание | Когда использовать |
|---------------|----------|-------------------|
| **`'gbdt'`** | Классический GBDT | По умолчанию, работает всегда ✅ |
| **`'dart'`** | Dropouts meet Multiple Additive Regression Trees | Для борьбы с переобучением |
| **`'goss'`** | Gradient-based One-Side Sampling | Для очень больших данных |
| **`'rf'`** | Random Forest | Каждое дерево на своей подвыборке (бэггинг) |

**Почему `'gbdt'`:**

```
- Стабильный, предсказуемый
- Хорошо изучен
- Лучше сходится при правильном tuning
- dart/goss требуют больше настройки
```

---

#### 4. `n_jobs: -1`

**Технически:**

```
Количество CPU ядер для параллелизма:

n_jobs = -1 → использовать все доступные ядра
n_jobs = 4 → использовать 4 ядра
n_jobs = 1 → однопоточный режим

LightGBM параллелит:
- Построение гистограмм (feature binning)
- Поиск лучших split'ов
- Обучение деревьев (при histogram-based алгоритме)
```

**Почему -1:**

```
Максимальное использование CPU:
- 8 ядер → 8 потоков
- 16 ядер → 16 потоков

Ускорение: ~6–8x на 8 ядрах (не линейное из-за overhead)
```

**Важно:** При использовании GPU (`device: 'gpu'`) этот параметр влияет только на:
- Предобработку данных
- Вычисление метрик
- Копирование данных CPU↔GPU

Основное обучение идёт на GPU.

---

#### 5. `verbose: -1`

**Технически:**

```
Уровень логирования:

verbose = -1 → silent (никаких логов)
verbose = 0 → только ошибки
verbose = 100 → лог каждые 100 итераций
verbose = 1 → лог каждую итерацию
```

**Почему -1:**

```
Обучаем 164 модели:
- При verbose=100: 164 × (1000/100) = 1640 строк лога
- При verbose=-1: 0 строк, чище вывод

Логи сохраняем программно (OOF AUC, feature importance).
```

---

#### 6. `device: 'gpu'` + `gpu_platform_id: 0` + `gpu_device_id: 0`

**Технически:**

```
device: 'gpu' → использовать GPU вместо CPU

gpu_platform_id: 0 → ID платформы OpenCL/CUDA
  - 0 = первая платформа (обычно NVIDIA)
  - 1 = вторая платформа (если есть, например, AMD + NVIDIA)

gpu_device_id: 0 → ID устройства внутри платформы
  - 0 = первая видеокарта
  - 1 = вторая видеокарта (если их несколько)
```

**Почему GPU:**

```
Ускорение обучения:

LightGBM на CPU:  ~15 минут на модель (800 деревьев, 750k × 400)
LightGBM на GPU:  ~3 минуты на модель

Ускорение: ~5x

Для 164 моделей:
  CPU: 164 × 15 мин = 2460 мин = 41 час
  GPU: 164 × 3 мин = 492 мин = 8.2 часа

Экономия: 33 часа
```

**Требования для GPU:**

```
- NVIDIA GPU с CUDA (Compute Capability ≥ 2.0)
- LightGBM собран с поддержкой GPU (pip install lightgbm --install-option=--gpu)
- Установлены CUDA Toolkit и cuDNN
```

**Почему platform_id=0, device_id=0:**

```
В системе может быть несколько GPU:
  platform_id=0, device_id=0 → первая видеокарта (NVIDIA RTX 3080)
  platform_id=0, device_id=1 → вторая видеокарта (NVIDIA RTX 3090)

Если GPU одна → оба параметра = 0.
```

## 4. Полный справочник параметров LightGBM

### 🔹 Основные гиперпараметры

| Параметр | Простыми словами | Технически | Типичные значения |
|----------|------------------|------------|-------------------|
| **`n_estimators`** | Сколько деревьев построить | Количество итераций бустинга (деревьев) | 100–2000 |
| **`learning_rate`** | Шаг обучения. Меньше = медленнее, но точнее | Шаг градиентного спуска η ∈ (0, 1] | 0.01–0.3 |
| **`num_leaves`** | Насколько глубокими будут деревья | Макс. количество листьев в дереве (не глубина!) | 15–255 |
| **`max_depth`** | Ограничение глубины дерева | Макс. глубина дерева (-1 = без ограничений) | -1, 8–16 |
| **`min_child_samples`** | Мин. примеров в листе | Мин. количество образцов в одном листе | 10–100 |
| **`subsample`** | Доля данных для каждого дерева | Доля строк, используемых на каждой итерации | 0.6–1.0 |
| **`colsample_bytree`** | Доля признаков для каждого дерева | Доля столбцов, используемых на каждой итерации | 0.6–1.0 |
| **`reg_alpha`** | L1-регуляризация | Штраф за абсолютную величину весов | 0–10 |
| **`reg_lambda`** | L2-регуляризация | Штраф за квадрат весов | 0–10 |
| **`scale_pos_weight`** | Балансировка классов | Вес положительного класса при дисбалансе | `neg/pos` |

---

### 🔹 Детальное объяснение ключевых параметров

#### 1. `n_estimators` + `learning_rate`

**Простыми словами:**

- `n_estimators` — сколько деревьев построить
- `learning_rate` — насколько сильно каждое дерево влияет на итог

**Аналогия:** Представьте, что вы готовите суп и добавляете соль:
- **Много деревьев + маленький шаг** (1000 деревьев, lr=0.03) = добавляете по щепотке 1000 раз. Точнее, но дольше.
- **Мало деревьев + большой шаг** (100 деревьев, lr=0.3) = добавляете по ложке 100 раз. Быстрее, но можно пересолить.

**Технически:**

```
F(x) = Σₜ η × hₜ(x)  где η = learning_rate, hₜ = t-е дерево

Меньше η → нужно больше n_estimators для сходимости
Но: меньше η → лучше обобщение (regularization effect)
```

**Рекомендация:**

```python
# Хорошие комбинации:
{'n_estimators': 300, 'learning_rate': 0.1}    # Быстро
{'n_estimators': 800, 'learning_rate': 0.05}   # Баланс
{'n_estimators': 1500, 'learning_rate': 0.03}  # Качество
```

---

#### 2. `num_leaves` vs `max_depth`

**Простыми словами:**

- `num_leaves` — сколько "концовок" (листьев) может быть у дерева
- `max_depth` — насколько глубоко можно ветвиться

**Важно:** LightGBM использует **leaf-wise** рост (по листьям), а не depth-wise (по глубине).

**Аналогия:**

```
Depth-wise (XGBoost, CatBoost по умолчанию):
        o           o
       / \         / \
      o   o       o   o
     / \ / \     /   / \
    o  o o  o   o   o   o
    depth=2     depth=2
    leaves=4    leaves=3

Leaf-wise (LightGBM):
        o           o
       / \         / \
      o   o       o   o
     /           / \
    o           o   o
                 \
                  o
    depth=2       depth=3
    leaves=3      leaves=4 ← растёт туда, где лучше split
```

**Технически:**

```
- num_leaves = 2^max_depth — теоретический максимум
- На практике: num_leaves < 2^max_depth для контроля переобучения
- Leaf-wise рост даёт меньшую ошибку при том же числе листьев, но рискует переобучиться
```

**Рекомендация:**

```python
# Для начала:
{'num_leaves': 31, 'max_depth': -1}  # LightGBM контролирует по листьям

# Если переобучение:
{'num_leaves': 15, 'max_depth': 8}
```

---

#### 3. `min_child_samples`

**Простыми словами:**

Минимальное количество клиентов в листе. Если меньше — дерево не будет делать такой split.

**Аналогия:**

Учитель не делит класс на группы, если в группе будет меньше 5 человек — слишком мелко.

**Технически:**

```
Меньше min_child_samples → больше листьев → выше риск переобучения
Больше min_child_samples → меньше листьев → выше bias, ниже variance

Особенно важно для:
- Шумных данных (увеличить до 50–100)
- Сбалансированных данных (20–50)
- Маленьких датасетов (5–20)
```

---

#### 4. `subsample` + `colsample_bytree`

**Простыми словами:**

- `subsample` — какую долю строк использовать для каждого дерева
- `colsample_bytree` — какую долю признаков использовать для каждого дерева

**Аналогия:**

4 повара готовят одно блюдо, но каждый:
- Берёт 80% продуктов (`subsample=0.8`)
- Использует 70% специй (`colsample_bytree=0.7`)

Итоговое блюдо — среднее всех 4 вариантов. Разнообразие снижает риск ошибки.

**Технически:**

```
Это форма стохастичности (стохастический бустинг):

subsample < 1.0 → каждое дерево видит случайную подвыборку строк
colsample_bytree < 1.0 → каждое дерево видит случайное подмножество признаков

Эффекты:
1. Снижение variance (ансамбль более разнообразный)
2. Защита от переобучения
3. Ускорение обучения (меньше данных на итерацию)

Типичные значения:
- subsample: 0.7–0.9
- colsample_bytree: 0.7–0.9
```

---

#### 5. `reg_alpha` + `reg_lambda`

**Простыми словами:**

Штрафуют модель за сложные веса. Чем больше штраф, тем проще модель.

**Аналогия:**

- **L1 (`reg_alpha`)** — штраф за количество ненулевых весов (обнуляет лишние)
- **L2 (`reg_lambda`)** — штраф за большие значения весов (сглаживает)

**Технически:**

```
L1 (Lasso): L = original_loss + α × Σ|wᵢ|
  → Обнуляет неважные признаки (feature selection)

L2 (Ridge): L = original_loss + λ × Σwᵢ²
  → Сглаживает веса, предотвращает экстремальные значения

Комбинация (Elastic Net):
  L = original_loss + α × Σ|wᵢ| + λ × Σwᵢ²
```

**Рекомендация:**

```python
# По умолчанию (часто работает хорошо):
{'reg_alpha': 0, 'reg_lambda': 0}

# Если переобучение:
{'reg_alpha': 1, 'reg_lambda': 5}

# Для очень шумных данных:
{'reg_alpha': 5, 'reg_lambda': 10}
```

---

#### 6. `scale_pos_weight`

**Простыми словами:**

Если положительных примеров мало, увеличиваем их важность.

**Аналогия:**

В классе 95 девочек и 5 мальчиков. Чтобы учитель не игнорировал мальчиков, он считает ответ каждого мальчика за 19 обычных ответов.

**Технически:**

```
scale_pos_weight = n_negative / n_positive

Пример:
- Positive: 1000 (1%)
- Negative: 99000 (99%)
- scale_pos_weight = 99000 / 1000 = 99

Это эквивалентно дублированию положительных примеров 99 раз,
но вычислительно дешевле.
```

**Рекомендация:**

```python
# Для сильно несбалансированных данных:
from sklearn.utils.class_weight import compute_class_weight

n_pos = (y_train == 1).sum()
n_neg = (y_train == 0).sum()
scale_pos_weight = n_neg / n_pos
```

### 🔹 Сравнительная таблица

| Критерий | LightGBM | CatBoost |
|----------|----------|----------|
| **Разработчик** | Microsoft (2017) | Yandex (2017) |
| **Основная фишка** | Leaf-wise рост + гистограммы | Обработка категориалов + ordered boosting |
| **Скорость обучения** | ⚡ Очень быстро | 🐌 Медленнее (но с GPU — быстро) |
| **Качество (AUC)** | 0.820–0.827 | 0.815–0.825 |
| **Память** | Эффективно | Требует больше RAM |

| **Интерпретируемость** | SHAP, feature importance | SHAP, feature importance, interaction |
| **Стабильность** | Чувствителен к гиперпараметрам | Менее чувствителен (out-of-box лучше) |

### 🔹 Ключевые отличия

#### 1. Рост деревьев

**LightGBM: Leaf-wise (по листьям)**

```
        o
       / \
      o   o
     /
    o
   /
  o
```

- Растёт туда, где наибольший прирост (gain)
- **Плюс:** Меньшая ошибка при том же числе листьев
- **Минус:** Риск переобучения на шумных данных

**CatBoost: Depth-wise (по глубине)**

```
        o
       / \
      o   o
     / \ / \
    o  o o  o
```

- Растёт симметрично по уровням
- **Плюс:** Стабильнее, меньше переобучается
- **Минус:** Может требовать больше деревьев для того же качества

---

#### 2. Обработка категориальных признаков

**LightGBM:**

```python
# Требует предварительного encoding
df['category'] = df['category'].astype('category').cat.codes
# или
df['category'] = LabelEncoder().fit_transform(df['category'])

# Или нативно (но менее эффективно):
model.fit(X, y, categorical_feature=['col1', 'col2'])
```

**CatBoost:**

```python
# Нативная поддержка — просто укажи названия столбцов
model = CatBoostClassifier(cat_features=['category1', 'category2'])
model.fit(X, y)

# Внутри: Ordered Target Encoding
# Для каждой категории считает среднее таргета,
# но использует только "прошлые" данные (no leakage)
```

**Технически:**

```
CatBoost использует Ordered Target Encoding:
- Для каждого объекта считает среднее таргета только по предыдущим объектам
- Это предотвращает data leakage и переобучение

LightGBM требует manual encoding (Label, One-Hot, Target)
```

---

#### 3. Борьба с переобучением

**LightGBM:**

```
Методы:
1. `num_leaves` — ограничение сложности
2. `min_child_samples` — мин. примеров в листе
3. `subsample` / `colsample_bytree` — стохастичность
4. `reg_alpha` / `reg_lambda` — L1/L2 регуляризация
5. `early_stopping` — остановка по валидации
```

**CatBoost:**

```
Методы:
1. **Ordered Boosting** — ключевое отличие!
   - Для каждого дерева использует пермутацию данных
   - Градиенты считаются только по "прошлым" объектам
   - Снижает bias и переобучение

2. `random_strength` — случайность при выборе split
3. `bagging_temperature` — температура для байесовского бэггинга
4. `l2_leaf_reg` — L2-регуляризация весов листьев
5. `early_stopping` — остановка по валидации
```

**Ordered Boosting (упрощённо):**

```
Обычный бустинг:
  Дерево 1: обучается на всех данных → градиенты смещены
  Дерево 2: обучается на градиентах от Дерева 1 → bias накапливается

Ordered Boosting (CatBoost):
  Пермутация данных: [x₃, x₁, x₄, x₂, ...]
  Дерево 1 для x₃: градиент = 0 (нет предыдущих)
  Дерево 1 для x₁: градиент от x₃
  Дерево 1 для x₄: градиент от x₃, x₁
  ...
  → Нет leakage, меньше bias
```

#### 4. Скорость и память

| Метрика | LightGBM | CatBoost |
|---------|----------|----------|
| **Обучение (CPU)** | 1–2 часа (750k × 2440) | 3–5 часов |
| **Обучение (GPU)** | 15–30 минут | 10–20 минут |
| **Память (RAM)** | 8–16 GB | 16–32 GB |
| **Предсказание** | Очень быстро | Быстро |

**Почему LightGBM быстрее на CPU:**

```
- Гистограммный алгоритм (binning признаков)
- Leaf-wise рост требует меньше итераций
- Оптимизированный C++ код с OpenMP
```

**Почему CatBoost быстрее на GPU:**

```
- Лучше распараллеливание
- Симметричный рост деревьев (легче векторизовать)
```

#### 5. Гиперпараметры: чувствительность

**LightGBM:**

```
Чувствителен к:
- `num_leaves` (сильно влияет на переобучение)
- `learning_rate` + `n_estimators` (взаимосвязаны)
- `min_child_samples` (особенно для шумных данных)

Требует тонкой настройки (Optuna, GridSearch)
```

**CatBoost:**

```
Менее чувствителен:
- Работает well out-of-the-box
- `depth` (6–10 работает почти всегда)
- `learning_rate` (0.03–0.1)
- `n_estimators` (500–1000 с early_stopping)

Можно использовать дефолтные параметры
```

### 🔹 Когда использовать что?

#### ✅ Выбирай LightGBM, если:

1. **Нужна скорость на CPU** — обучаетесь на ноутбуке/сервере без GPU
2. **Большие данные** (>1M строк, >1000 признаков) — эффективнее по памяти
3. **Уже есть encoding** — категориальные признаки уже обработаны
4. **Нужен контроль** — хочешь точно настроить каждый аспект
5. **Ансамбли** — легко обучить 10–20 моделей для блендинга

```python
# Типичный use case:
lgbm = LGBMClassifier(
    n_estimators=800,
    learning_rate=0.05,
    num_leaves=63,
    min_child_samples=30,
    subsample=0.75,
    colsample_bytree=0.75,
    reg_alpha=1,
    reg_lambda=5,
    early_stopping_rounds=50,
    verbose=100
)
```

---

#### ✅ Выбирай CatBoost, если:

1. **Много категориальных признаков** — нативная поддержка без encoding
2. **Нужно качество out-of-box** — меньше времени на настройку
3. **Есть GPU** — обучается быстрее LightGBM на GPU
4. **Маленькие/средние данные** (<500k строк) — разница в скорости не критична
5. **Нужна интерпретируемость** — лучшие инструменты для анализа (interaction, shap values)

```python
# Типичный use case:
catboost = CatBoostClassifier(
    iterations=1000,
    learning_rate=0.03,
    depth=8,
    l2_leaf_reg=5,
    random_strength=1,
    bagging_temperature=0.7,
    cat_features=['cat1', 'cat2', 'cat3'],
    early_stopping_rounds=50,
    verbose=100,
    task_type='GPU'  # или 'CPU'
)
```
